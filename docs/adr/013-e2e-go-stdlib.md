# 013. e2e テストは Go の標準ライブラリだけで書く

- 状態：採用
- 日付：2026-10-17
- 関連：`e2e/`

## 状況

e2e テストは、ブリッジを起動して HTTP でリクエストを送り、偽の ABS・goPodder が受け取ったものを確かめる。シナリオを読みやすく書ける道具として、YAML の手順書で API のシナリオテストを書く [runn](https://github.com/k1LoW/runn) を検討した。

試したところ、偽のサーバー（httpstub）の受信記録を `runn.Func` で登録すれば、手順書から確かめられることは分かった。一方で、次の点も分かった。

- 依存が 182 モジュール（vendor にすると 220MB）
- runn v1.11.1 は Go 1.26 以上が必要（ブリッジは Go 1.25）
- 当時のテストは、ネットワークにつながらないコンテナで動かしていた

## 選択肢

| 観点 | Go だけ | runn ＋ Go |
|---|---|---|
| 実行環境 | 標準ライブラリだけで動く | 依存の取得と Go 1.26 への更新が要る |
| 手順の多いシナリオ（POST → GET など） | 補助関数があれば同じくらい短い | いちばん読みやすい |
| 規則の表（7.2 節の判定表など） | テーブル駆動で 1 ケース 1 行。明らかに短い | ケースごとに手順書が要る |
| 偽のサーバーの設定と確認 | 同じ言語で直接触れる | Go の関数か管理用の API を挟む |
| 仕組みの数 | Go だけ | YAML と Go の 2 層 |

## 決定

Go の標準ライブラリだけで書く。runn は使わない。

## 結果

- この仕様は、送った内容の確認と規則の表が多く、純粋なシナリオは 5.1 節と 5.2 節くらい。runn が得意な部分は全体の一部にとどまる。
- 失うのは「YAML の手順書として読める」ことだけ。読みやすさは、[014](014-e2e-dsl-diagrams.md) の DSL と図で補う。
- 手順の多いシナリオが増えて読みにくくなったら、その部分だけ runn を足すこともできる。
