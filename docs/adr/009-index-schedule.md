# 009. 索引を cron 式で定期的に作る

- 状態：採用
- 日付：2026-10-19（C2・C3）、2026-10-26（cron の書き方）
- 関連：[仕様](../spec.md) 2.1 節・6.3 節（元の論点 C2・C3）

## 状況

AntennaPod の記録は、エピソードを URL と GUID でしか表さない。ABS には「この URL のエピソードはどれか」を問い合わせる API がないので、ブリッジは ABS の全エピソードの一覧（索引）を手元に持ち、その中から探す。

最初の仕様では、索引を次のときに作り直していた。

1. 前回作ってから 5 分（`ABS_INDEX_TTL_SECONDS`）を過ぎたあとの同期や記録の受信
2. 照合できない記録が来て、索引を作ってから 10 秒以上経っているとき

ところが、ABS にない番組（元の配信元のフィードで購読している番組）の記録は、作り直しても必ず照合できない。そうした記録が届くたびに 2 が起き、最短 10 秒おきに全部の作り直しが走りうる。索引を 1 回作るには、番組が 50 あれば約 53 回のリクエストが要る。

また、2 の「1 回だけ作り直す」が記録 1 件ごとか、リクエスト 1 回ごとかも決まっていなかった（C3）。

## 選択肢

- 照合できない記録が来たら、更新時刻の変わった番組だけを取り直す（当初の推奨）
- 決まった時刻に索引を作る（利用者の提案）

利用者の環境では、ABS にエピソードが追加されるのが特定の時間帯に限られる。

## 決定

決まった時刻に作る方式を採る。

- 索引は、`ABS_INDEX_SCHEDULE` の cron 式で指定した時刻に作る（例：`30 7 * * *`）。`@every 15m` のような間隔も同じ変数で書ける。既定は `@every 15m`。
- ブリッジを起動したときにも 1 回作る。
- 作るのに失敗したら、前の索引を使い続け、warn ログを出す。
- 照合できない記録が来ても作り直さない。5 分の使い回しと 10 秒の制限は仕様から外す。C3 の決まりも要らなくなった。
- 毎回全部を作り直す。番組の詳細は `POST /api/items/batch/get` でまとめて取る。フィード一覧（[001](001-feed-url-mapping.md)）も同じときに取る。
- cron 式の解釈には `github.com/robfig/cron/v3` を使い、その標準の書き方に合わせる（2026-10-26）。
  - 曜日は `0`〜`6`（`0` が日曜日）。`7` は不正。
  - 月と曜日は `JAN`・`MON` のような名前でも書ける。
  - `@hourly`・`@daily`・`@weekly`・`@monthly`・`@yearly` も受け付ける。

## 結果

- 照合できない記録が続いても、ABS への負荷は増えない。
- 索引を作ってから次に作るまでの間に ABS に追加されたエピソードは、照合できない。たとえば 06:00 に追加され、索引を 07:00 に作るなら、06:30 に AntennaPod で聴いた記録はそのときは反映されない。ただし記録は goPodder に残るので、07:00 のあと AntennaPod が次に同期したときの突き合わせで反映される。
- 新しいエピソードがフィード一覧に載るのは、AntennaPod がフィードを更新したあと。作る時刻は、エピソードが追加される時間帯の少し後にするとよい。
- cron の書き方の 3 点は、ライブラリの標準の動きのまま受け入れた。弾くための処理を足すと、ライブラリに置き換えた意味が薄れるため。
- cron 式をどのタイムゾーンで解釈するかは [010](010-timezone.md) で決めた。
