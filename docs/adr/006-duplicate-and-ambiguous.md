# 006. 同じエピソードに複数の記録・複数の候補があるとき

- 状態：採用
- 日付：2026-10-17
- 関連：[仕様](../spec.md) 5.2 節・6.2 節（元の論点 B3・B6）

## 状況

**同じ ABS エピソードに、別々の URL の記録が複数ある**（B3）

gPodder の記録は、エピソードを「番組のフィード URL」と「音声ファイルの URL」の組で表す。同じエピソードでも URL が違えば、goPodder では別の記録になる。たとえば次のときに起きる。

- 同じ番組の購読を、元の配信元のフィードと ABS のフィードの間で切り替えた
- 元の配信元が、GUID は変えずに音声ファイルの URL だけを変えた（計測サービスの付け替えや CDN の移行など）。AntennaPod は GUID で同じエピソードと判断し、以降は新しい URL で記録を送る

ABS にまだ進捗がなく（ブリッジを入れた直後など）、新旧両方の記録があると、処理の順番によっては古い記録の位置が ABS に残り、次の同期で AntennaPod に書き戻されて巻き戻る。

**1 つの記録に、ABS のエピソードが複数当てはまる**（B6）

たとえば、同じ番組を ABS の 2 つのライブラリ（「ポッドキャスト」と「アーカイブ」）に登録していると、元の配信 URL で探したときに 2 つのエピソードが当てはまる。仕様には「照合できない」とあったが、次の方法（GUID）で探し直すのかが読み取れなかった。

## 選択肢

- B3：同じ ABS エピソードへの記録を 1 つにまとめる ／ まとめず、処理の順番だけを決める
- B6：照合できないとして止める ／ 次の方法で探し直す

## 決定

- **B3**：まとめない（考慮外とする）。ただし GET の突き合わせでは、記録を**時刻の古い順**に処理する。同じ ABS エピソードに複数回反映しても、最後に残るのが最も新しい記録になる。
- **B6**：その記録は「照合できない」とし、次の方法では探さない。

## 結果

- AntennaPod は基本的に ABS のフィードで購読する前提なので、B3 の状況はまれ。まれな状況のために、まとめる仕組みを入れない。古い順に処理するだけで、巻き戻りは防げる。
- B6 は今の運用では起きない。違うエピソードを書き換えてしまうより、反映しない方が安全。例の場合は GUID も同じなので、探し直しても決まらないことが多い。
