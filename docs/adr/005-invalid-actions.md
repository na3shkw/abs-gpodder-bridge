# 005. 時刻のない記録や、値のおかしい記録の扱い

- 状態：採用
- 日付：2026-10-17（B2）、2026-10-19（C4・C5）、2026-10-26（数値の形式）
- 関連：[仕様](../spec.md) 5.1 節・5.2 節・11.1 節・11.2 節（元の論点 B2・C4・C5）

## 状況

gPodder の記録には、ふつう「いつ聴いたか」（`timestamp`）と再生位置（`position`）が入る。ただ、送るアプリの作りや不具合によって、次のような記録もありうる。

- **時刻がない**（B2）：仕様は、時刻のない記録を「ブリッジがそのリクエストを受け取った時刻」とみなす。POST なら自然だが、GET の突き合わせでは goPodder に保存済みの過去の記録を取り出すので、時刻のない古い記録が同期のたびに「たった今聴いた」扱いになる。たとえば ABS の Web 画面で 30 分まで聴いても、goPodder にある時刻のない「10 分」の記録が新しいとみなされ、同期のたびに 10 分へ巻き戻される。
- **位置がおかしい**（C4）：POST では「位置が 0 以上の数値の記録だけ」を反映すると決めていたが、GET では「位置を持つ記録」としか書かれていなかった。`-5` や `"abc"` の記録が goPodder に入ると、GET でだけ対象になるように読めた。
- **想定外の時刻の書式**（C5）：`2026-10-17T18:00:00+09:00` のような時差付きや、`yesterday` のような時刻として読めない値の扱いが決まっていなかった。

なお AntennaPod は、記録を作る 8 か所すべてで作成時の時刻を設定し、送るときも必ず `timestamp` を書き出す（AntennaPod 3d105d5 で確認。`EpisodeAction.writeToJsonObject`）。書式は UTC の `YYYY-MM-DDTHH:MM:SS`（Z なし）。

## 選択肢

- B2：(a) GET では時刻のない記録を突き合わせの対象にしない ／ (b) 時刻のない記録を「とても古い」とみなす ／ (c) 今のまま
- C4：POST と GET でそろえる ／ そろえない
- C5：時差付きを受け付ける ／ 受け付けない

## 決定

- **B2**：(a) を採る。GET の突き合わせでは、時刻のない記録を対象にしない。POST で届いたときは、今までどおり「受け取った時刻」として扱う。
- **C4**：GET でも「位置が 0 以上の数値」の記録だけを対象にし、POST とそろえる。
- **C5**：時差付きの時刻は受け付けて UTC に直す。時刻として読めない値の記録は、無効として無視する。
- **数値の形式**（実装者が決め、2026-10-26 に利用者が承認）：`position`・`total`・`started` は JSON の数値だけを受け付ける。`"position": "120"` のように文字列で届いた記録は無効として無視する。**この点は仕様書には書かれていない。**

## 結果

- AntennaPod だけを使う限り、時刻のない記録は goPodder に入らない。入るのは、ほかのアプリを同じアカウントで使った場合か、API を直接使った場合に限られる。
- B2 は当初 (b) を推奨していたが、AntennaPod の調査を受けて (a) に変えた。(b) でも問題はないが、「とても古い」とみなす扱いの説明とテストが余分に要る。
- ほかのアプリの時刻のない記録も、POST のときには ABS に反映されるので、失われるものは小さい。
- 数値の形式は AntennaPod が数値で送るので、ふだんの運用では影響しない。実装者が自分で書いたテスト（`internal/bridge`）で守られている。
